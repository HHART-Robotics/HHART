# HHART template

Starting point for a new robot. `hhart new` copies this folder and renames
`robot1`. It runs on a laptop without hardware or ROS using the loopback
device. ROS parts support ROS 2 Jazzy only for now. Paths below are relative
to `software/`.

## Evaluation

HHART has been evaluated on one robot, MICROPIRO, a tracked sewer inspection
robot at UTS. This template is MICROPIRO's structure with the robot-specific
code removed. Details are in the paper, see
[Citing](https://github.com/HHART-Robotics/HHART#citing).

MICROPIRO was built in two versions on one core, one reaching the hardware
through Teensy firmware and one through ROS 2 Jazzy and `ros2_control`.
Results:

- 278 tests pass on a Windows laptop without ROS or hardware, in 2.8 s.
- Seven planted rule violations each failed the build.
- The operator UI worked unchanged against both versions, from a laptop and an
  Android tablet.
- RViz, `rqt` and `rosbag2` worked on the robot while the operator was
  connected.
- Five mid-drive failure cases were each stopped by the intended layer, all but
  one within 10 ms of its bound.

Limitations: one robot, one developer, Python only, bench tests rather than in
a pipe. The template itself hasn't run on hardware, and the contract registry
hasn't been used on a robot yet.

## Rules

| # | Rule | In this tree |
| --- | --- | --- |
| 1 | **Operators never see ROS.** Every operational function runs on the everyday systems the partner's staff already use, such as Windows, macOS, Android or iOS, without a terminal, and the operator never knows that ROS exists; any ROS stays on the robot or in an isolated environment, e.g. Docker or WSL. | `apps/web/` |
| 2 | **The core is the centre.** Logic resides in a core without input, output or ROS; ROS is an adapter, not the layer everything stems from. | `python/src/robot1/core/`, `apps/web/src/core/`, `apps/api/core/` |
| 3 | **One command path.** The operator, ROS and tests command through one port, behind which sit validation, arbitration and the deadman. | `core/ports.py`, `core/session.py`, `hhart.arbitration` |
| 4 | **Conventions in the core.** The ecosystem's conventions are pure functions in the core, tested without ROS; only the client library stays in its adapter. | `core/protocol.py`, `core/ros_messages.py` |
| 5 | **ROS by role.** ROS is placed by role: hardware integration inside the robot, where its drivers are used, and research access at its edge, on demand. | `ros/`, `adapters/ros/node.py` |
| 6 | **Contracts at the boundary.** Only contracts defined in the core cross the robot's boundary, and faults reach the operator in the contract's terms. | `core/contract.py`, `core/health.py`, `CONTRACT.md`, `adapters/operator_server.py`, `adapters/ros/passthrough.py`, `apps/web/src/core/`, `@hhart/ui` |
| 7 | **Device ownership.** An adapter runs in the process that owns the device it commands, and each actuator command interface has one publisher. | `adapters/firmware_link.py`, `adapters/ros/devices.py` |
| 8 | **Layered stop.** A host deadman covers every source, and a lowest tier stops the actuators whatever sent the last command, within derived bounds. | `core/session.py` (P and T; the host deadman is `hhart.arbitration`), `firmware/robot1/` (software and hardware watchdogs), `ros/robot1_bringup/config/controllers.yaml` |
| 9 | **Checked in the build.** Tests over the source fail the build when a rule breaks, and every program loads without ROS; firmware keeps its own rules. | `python/tests/test_architecture.py`, `python/tests/test_firmware.py`, `apps/web/architecture.test.ts`, `apps/api/architecture.test.ts`, `firmware/robot1/test/` |
| 10 | **Unattended deployment.** No engineer is needed: the robot starts at power-on and recovers from its own faults without anyone logging in, and ships with any middleware pinned. | `deploy/systemd/`, `ros/robot1.repos` |

## Layout

```text
software/
  CONTRACT.md               operator contract, generated by hhart contract
  python/                   robot package (pip or colcon)
    src/robot1/
      core/                 logic, no I/O or ROS. contract.py defines the contract
      adapters/             operator server, firmware link, loopback, ros/
      apps/                 entry points: bridge.py (embedded), robot.py (full ROS 2)
    tests/
  apps/                     deployable TypeScript apps
    web/                    operator UI, builds to dist/
    api/                    optional recordings API
  firmware/robot1/          PlatformIO project (embedded route)
  ros/                      colcon packages and robot1.repos (full ROS 2 route)
  deploy/systemd/           service units
.github/workflows/ci.yml
```

## Routes

Two ways to reach the hardware. Everything above the device adapter is shared.

| | Embedded | Full ROS 2 |
| --- | --- | --- |
| Hardware via | `firmware/` | drivers and `ros2_control` in `ros/` |
| Entry point | `apps/bridge.py` | `apps/robot.py`, launched by `robot1_bringup` |
| Device adapter | `adapters/firmware_link.py` | `adapters/ros/devices.py` |
| ROS on the robot | Optional, off by default | Required |
| Last-resort stop | Firmware watchdog | Controller timeout, then firmware watchdog |
| Service | `robot1.service` | `robot1-ros.service` |
| Without hardware | `robot1-bridge --port loopback` | `mock_components` in `robot1.urdf` |

Keep one route with `hhart new myrobot --route embedded` (or `ros`). With both,
switch on the robot:

```bash
sudo systemctl disable --now robot1 && sudo systemctl enable --now robot1-ros
```

## Contract

Defined in `python/src/robot1/core/contract.py`.

| | Tier 1 | Tier 2 |
| --- | --- | --- |
| What | Commands, faults, state the UI depends on | Extra ROS topics, read-only |
| Declared with | `@CONTRACT.message` on a frozen dataclass | `CONTRACT.passthrough(...)` |
| Direction | Both | Robot to operator |
| Routes | Both | Full ROS 2 only |
| UI | Needs a view | Shown in a generic panel |

The robot sends `describe` on connect and the UI ignores unknown types, so
adding messages or fields doesn't break it. Bump `CONTRACT.version` on renames
or removals. After changing `contract.py`, run `hhart contract` to regenerate
`CONTRACT.md` and the UI's golden fixture.

Tier 2 tests (`tests/ros/`) need ROS 2 Jazzy sourced. CI runs them in
`ros:jazzy`.

## ROS tools

On either route, `adapters/ros/` adds the robot to the ROS graph as a node, so
RViz, `rqt` and `rosbag2` work on the robot while an operator is connected. ROS
message conversions are pure functions in `core/ros_messages.py`, tested
without ROS.

## Run

```text
cd software/python
uv venv && source .venv/bin/activate     # Windows: .venv\Scripts\activate
uv pip install -e ".[dev]" "hhart @ git+https://github.com/HHART-Robotics/HHART.git@vHHART_VERSION#subdirectory=python"
pytest
hhart check ../..
robot1-bridge --port loopback
```

UI, from the repo root:

```text
pnpm install
pnpm dev                                 # http://localhost:3000
pnpm test && pnpm typecheck
```

Firmware:

```text
cd software/firmware/robot1
uvx --from platformio pio test -e native
uvx --from platformio pio run -e teensy40 -t upload
```

On the robot, full ROS 2 route, with the repo cloned to `~/ws/src/robot1`:

```bash
cd ~/ws
vcs import src < src/robot1/software/ros/robot1.repos
rosdep install --from-paths src --ignore-src -y
colcon build && source install/setup.bash
ros2 launch robot1_bringup robot1.launch.py
```

Embedded route: see `deploy/systemd/robot1.service` for the venv setup. Either
way, `robot1-web.service` serves the UI on port 8080.

Notes:

- Motors stay off until `firmware/robot1/src/hw_watchdog.cpp` is implemented
  for your board (Rule 8).
- After an operator stop, ROS and tests can't drive until the operator sends
  `release` (Rule 3).
- A device that keeps publishing the same value is reported as stale (Rule 6).
- Prefer standard ROS messages. Custom ones need a `robot1_interfaces` package.

## Making it yours

1. `python/src/robot1/core/contract.py`: your messages, then `hhart contract`.
2. `core/ros_messages.py`: measure `MAX_MPS` and `TRACK_M` on the robot. Match
   them in `controllers.yaml` and `robot1.urdf`.
3. `core/session.py`: set `DEADMAN_PERIOD_S` and `DEADMAN_TIMEOUT_S` so T + P
   fits your stop bound.
4. Hardware. Embedded: `adapters/firmware_link.py`, `applyMotors` in
   `firmware/robot1/src/main.cpp` and `src/hw_watchdog.cpp`. Full ROS 2:
   drivers in `ros/robot1.repos`, `adapters/ros/devices.py`, and your hardware
   interface in place of `mock_components`.
5. `apps/web/src/robot/scene.ts`: your 3D model and environment. Your own views
   go in `apps/web/src/`.
6. `deploy/systemd/`: user and paths.
